TypeSafe · System One

Jev 实测笔记

一个不生成文本的模型。给它材料和带类型的问题，它还你带概率的判断 —— 下面是把它跑穿之后，值得记住的东西。

它是什么

它不是便宜版 GPT，它替代的是 if

LLM 把文本变成文本，你再写解析器去猜结构。Jev 把文本变成类型，答案空间由你定义。

TypeSafe 管这叫 System One 模型 —— 取自 Kahneman 的双系统理论。System 2 是慢速推理， LLM 的主场；System 1 是快速直觉判断：「这条工单是不是投诉？」「这段话的语气多冲？」

绝大多数软件真正需要的是后者：一个能直接喂给 if 的判断。 但今天大家都在用 System 2 的模型干 System 1 的活 —— 求 GPT 吐一段 JSON， 然后解析、校验、处理幻觉、处理格式漂移、重试。Jev 把这一层整个砍掉了。

Jev（System One）

  • 输出 类型化、受约束
  • 答案空间 你定义，模型只能从中选
  • 概率 针对真实结果标定过
  • 延迟 实测 0.5s 量级，与问题数几乎无关
  • 计价 $0.042 / 百万 input，output 免费
  • 做不到 写任何一个字的自由文本

LLM（System Two）

  • 输出 自由文本
  • 答案空间 开放，靠 prompt 约束
  • 概率 未针对准确度标定
  • 延迟 随输出长度线性增长
  • 计价 input + output 都计费
  • 做不到 结构上保证合法

「答案空间由你定义」是结构性的，不是概率性的：Choice 只能返回你给过的某个 key， 不可能返回一个你没写过的字符串。这和「我用 prompt 求 LLM 只返回这几个词」有本质区别。

一次请求

整个 API 只有一个端点

POST /v1/systemone。三件套：state（要评估的材料）、 questions（要做的判断，每个带类型和答案空间）、model。 N 个问题对同一份 state 并行评估、互相独立。 

# state 是材料，questions 是判断 —— 别把结论塞进 state
{
  "model": "jev-latest",
  "state": "My card was charged twice for invoice INV-9921.",
  "questions": {
    "billing": {"type":"noul",   "instructions":"The message is about a billing problem."},
    "team":    {"type":"choice", "instructions":"Which team should handle this?",
                 "criteria":{"billing":"Payments", "technical":"Bugs", "sales":"Pricing"}},
    "urgency": {"type":"score",  "instructions":"How urgent?",
                 "criteria":["can wait", "this week", "today", "right now"]}
  }
}

返回的不是一段需要解析的文本，而是三个可以直接进 if 的值。 其中 urgency 这一项最值得看：

scoreurgency — 这事多急？
0 · can wait0.04
1 · this week0.50
2 · today0.43
3 · right now0.03
score 1.45confidence 0.48

模型如实告诉你它在两档之间摇摆。score 是概率加权的期望值， 所以落在 1.45 —— 比「这周」急，比「今天」松。一个硬分类会丢掉这个信息。

原语

只有三种问题

三种可以在同一次调用里混用。要开关用 Noul，要分派用 Choice，要排序或比较用 Score。

Noul

「这句陈述是真的吗？」

criteria
可选，用来钉死 true / false 的边界
返回
noul：0~1 概率
注意
没有单独的 confidence —— 概率本身就是信号。instructions 写陈述句，别写疑问句

Choice

「是哪一个？」无序选项里挑一个。

criteria
必填，≤ 255 项（实测 256 → HTTP 400）
返回
choice + probabilities + confidence
注意
永远留一个兜底选项。没有兜底，模型被迫在不合适的选项里硬选

Score

「在哪一档？」有序档位上打分。

criteria
有序数组，上限 10 档（11 → 400）
返回
score（可落在档位之间）+ legend + 分布 + confidence
注意
档位描述要写可观察的特征，不要写程度副词

实测一个彩蛋：255 个选项里选出目标项，置信度仍然 1.0。 大规模分类 —— 商品类目、技能目录、意图集 —— 是可行的。

这条决定了 Jev 的正确用法

40 倍问题量，延迟不变，成本只涨 2.7 倍。 因为 state 只发一次，增量只有问题文本；而 output token 不计费。

所以正确姿势不是「先分类，再根据分类追问」，而是把整棵决策树的所有问题一次问完， 包括那些可能用不上的，让代码去挑哪些有意义 —— 官方管这叫投机性扇出。

实际效果：工单分诊里一次问 8 个问题，其中 bug_severity 只在分类是 bug 时有意义， refund_requested 只在分类是账单时有意义。全问，零额外往返。 横切标记（frustration / legal_threat / deadline） 不属于任何分支、对所有工单都适用 —— 扇出让这类全局标记变得几乎免费。

实测 · 第二课

官方列了 9 类弱点，实测只有 1 类真的翻车

官方的 model-jaggedness 页面列了九类失败模式，但没给任何量化数据。 逐条压测（真值 vs 模型输出）：

场景期望实测判定
计数 17 项17→高，16/18→低0.99 / 0.01 / 0.01PASS
日期窗口（让模型自己算天数）≈0.0（实际 42 天 > 30 天）0.26 · 0.29 · 0.32FAIL
同题，代码先算好 days=42≈1.00.99PASS
双重否定≈1.00.92 – 0.93PASS
噪声淹没信号（夹在 240 句废话中）与干净输入一致auth(1.0) == auth(1.0)PASS
state 内提示注入≈0.00.01PASS
P(x) + P(¬x)不保证 = 10.02 + 0.97 = 0.99PASS
中文（非主力语言）能判对anger=2.95，类别=物流(1.0)PASS
数值接近（0.1452 vs 0.15）≈1.00.86勉强
十六进制颜色接近≈1.00.90勉强

日期这条，危险的不是答错

是答成 0.26 这种模棱两可的值 —— 既不是「是」，也不是明确的「否」。 任何阈值都救不了你。跨三次运行稳定复现。 

# 差 —— 让模型自己算日期差
Noul("The return request is within the policy window.")
-> 0.26   错，而且模糊

# 好 —— 代码算好天数放进 state，模型只做判断
state = {..., "days_elapsed": 42, "policy_days": 30}
Noul("`days_elapsed` exceeds `policy_days`.")
-> 0.99   干净

# 最好 —— 这题根本不该问模型
days_elapsed > policy_days
通用规则

算术在代码里做，判断才交给模型。 分桶是判断（「大概过了多少天」→ 31to60，conf 0.97，模型行）； 算差值是算术（模型不行）。

抗噪声和抗提示注入的表现好于文档预期 —— 但官方原话是「不默认把数据当敌意输入」， 不是保证。生产环境仍需自己的纵深防御：用户内容放进 state 的具名字段， 而不是拼进 instructions。

实测 · 第三课

置信度是第二根轴

choice 告诉你是什么；confidence 告诉你敢不敢自动执行。 LLM 给不了你第二根轴 —— 它对着一个完全模糊的输入，也会用同样自信的语气给你一个答案。

阈值跟着动作的风险走，不跟着模型走。同一个系统里，查余额可以 0.6 放行， 批转账要 0.85 甚至要人确认。风险容忍度编码在你的代码里。

低置信度如实反映「多意图」

自然语言转函数调用的 demo 里，这句话把置信度打到了 0.38：

choice“make the living room a bit warmer and dim the lights”
set_temperature0.48
set_lights0.40
play_music0.06
其余三项0.06
confidence 0.38→ 反问用户，不猜

这是个双动作请求。模型没有硬选一个，而是把概率劈成两半。 生成式 function calling 通常会自信地只调一个工具。

实践建议：配一个 multi_step 的 Noul 一起扇出，主动检测多动作并拆分请求， 而不是事后从 confidence 反推原因。低置信度有三种成因 —— 输入本身模糊（反问）、多意图（拆分）、你的选项设计有重叠（这是你的 bug）—— 别一律当成「转人工」。

但 confidence 防「模糊」，不防「问错问题」

同一个 demo 里的另一条，置信度 0.99，答案是错的：

"lock up, I'm going to bed"
  -> lock_doors(room=bedroom)   confidence = 0.99

# 我问的是   : "Which room is mentioned?"        <- bedroom 确实被提到了
# 我想问的是 : "动作发生在哪个房间"               <- 模型没错，问题写错了
字面理解 —— 实际开发里最高频的坑

Jev 回答你写的问题，不是你想问的问题。 instructions 要写精确的判定条件，不是意图；边界情况直接写进 criteria 的 not_for / examples。

这类坑只有拿真实样本回归测试才会暴露 —— 压测表里看不见它。

落地

它在生产链路里的位置

Jev 不替代 LLM，它在 LLM 前后各架一道便宜的闸门： 把不该进 LLM 的请求挡住、把 LLM 的输入收窄、把输出核对一遍。

Jev护栏扇出 — 越狱 / PII / 越界 / 有害，5 道并行检查0.5s · $0.00003
Jev意图路由 + 枚举参数扇出，答案空间封闭0.5s · $0.00003
代码置信度达标 → 确定性 handler（查余额、改设置）根本不需要 LLM—
检索向量召回 20 段候选—
Jev重排 + 截断 — 相似度之上再加一层「是否真的回答了问题」0.5s · $0.00005
LLM拿着 2~3 段证据生成回复~3s · $0.01
Jev输出护栏 — 幻觉 / 引用核对 / 语气0.5s · $0.00003

整条链路里 Jev 那四步加起来不到 LLM 那一步成本的 1.5%。

四种官方模式，一句话各自

投机性扇出 —— 一次问完，代码挑。 置信度闸门路由 —— 阈值按动作风险设。 复合打分 —— 把复杂判断拆成原子分，权重放在你的代码里（可读、可调、可 A/B）， 而不是让模型直接给总分。 意图路由 —— 答案空间封闭，结构上不可能路由到不存在的 handler。

两个踩坑提醒

本机若有 SOCKS 代理，官方 SDK 底层的 httpx 会报 ImportError: socksio —— 补装 socksio 即可。 另外文档说 Score 档位 2~10，实测下限没有被服务端强制（1 档也能通过）， 只有上限 10 是硬限制。
